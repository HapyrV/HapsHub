# HapsHub foundation baseline, 2026-11-08

Taken before any HapsHub feature work, so later builds have something to compare against.
Measure with `tools/hapshub/measure-idle.ps1`, which sums the app, its watchdog and its WebView2 children.

## Idle use

Windows 10, 16 logical cores, window hidden in the tray, not in VR. One 60 s sample per row.

| Build | Config | Photino native | .NET | Uptime | Working set | Private | CPU | GPU memory |
|---|---|---|---|---|---|---|---|---|
| Installed 2026.62.3 | Release | fork | 9 | 4 min | 404 MB | 355 MB | 0.05% | 18 MB |
| `foundation/net10` | Release | fork | 10 | 4 min | 465 MB | 378 MB | 0.19% | 20 MB |
| Stock clone, `0bfb467f` | Debug | NuGet 4.0.22 | 9 | 4 min | 756 MB | 434 MB | 0.37% | 45 MB |
| Installed 2026.62.3 | Release | fork | 9 | 406 min | 389 MB | 2,758 MB | 0.29% | 0 MB |

How far to trust these:

- Each row is a single run. The gap between the first two rows is small enough to be noise, so it does not show that .NET 10 costs more or less than .NET 9.
- The stock clone row is not comparable to the others. It is a Debug build on a different native DLL, and its window had been shown and hidden just before sampling.
- Working set at 45 s varied from 70 MB to 264 MB between runs, so early readings are not useful. Settle for at least 3 minutes.

## Open: private memory growth

The installed app's main process held 2,438 MB private after 406 minutes in the tray, against 110 MB at 4 minutes. Its working set stayed at 184 MB. The cause is unknown, and the `foundation/net10` build has not had a long run yet. `AppShell` has a `_memDiagTimer` that may help.

## Startup and build

- First window: installed 2.3 s, `foundation/net10` 3.2 s, stock clone 3.2 s. One run each.
- `foundation/net10` builds with 0 errors and 138 unique warnings, all from C# code, mostly nullable annotations. The earlier stock build recorded 142, possibly counted differently.

## Photino native DLL

The app depends on the fork's `Photino.Native.dll`, which has 28 exports the NuGet package lacks (surfaces, composition hosting, resource suspension, `SetBackgroundColor`). `build-native.cmd` needs the MSVC v143 C++ tools, which this machine does not have. Without them, the build falls back to the NuGet DLL. The app still starts, but those features are missing.

Current stopgap: the two DLLs are copied from the installed app, which was built from the same submodule commit, `0092ce91`. The destination is git-ignored, so a fresh clone needs this step again:

```powershell
$dst = 'external\photino.NET\Photino.Native\Photino.Native\x64\Release'
New-Item -ItemType Directory -Force $dst
Copy-Item "$env:LOCALAPPDATA\VRCNext\current\Photino.Native.dll", "$env:LOCALAPPDATA\VRCNext\current\WebView2Loader.dll" $dst
```

Install the C++ workload once native code has to change.

## Running test builds

Until the rename and the path service land, a dev build shares everything with the installed app:

- `Global\VRCNext` lets only one copy run, so the installed app has to exit first.
- All data comes from `%APPDATA%\VRCNext`, including the real login and databases. `GetFolderPath` cannot be redirected from outside the app.
- Each start repoints `vrcn://` at that exe. Starting the installed app again restores it.
- With `MinimizeToTray` on, closing the window only hides it. The only clean exit is the tray menu.
- If a test build has to be ended from a script, delete `Logs\session.sentinel` first. Otherwise the watchdog writes a false crash report and the next start shows it.
